# Application Autofill (Chrome extension, MV3)

Personal Chrome extension that fills job applications from a saved profile. Workday, Greenhouse, Ashby, Lever, Gem, iCIMS and Rippling are supported; YC Work at a Startup drafts the note to the founder (unverified until tested on a real page). Loaded unpacked from this folder; after edits, reload it in chrome://extensions (no build step).

## Files
Content scripts are split into shared modules and one adapter per portal. They are classic scripts that share one namespace object, `globalThis.AAF`, in the extension's isolated world. Each file is an IIFE guarded by `AAF.once(name)` (against re-injection) that reads what it needs from `AAF` and adds its exports to it. Load order is the manifest `content_scripts.js` list; the popup's injection fallback reads the same list.
- `shared/core.js`: namespace, `DEBUG`/`dbg`/`show` logging, `norm`, `sleep` / `delay` / `now` / `focusStep` / `focused` / `fillClock` (background-tab scheduling and pausing, see Rules), `waitFor`, `visible`, `SKIP`, `parseDate`, `splitAlts`, `checkboxOn`. `AAF.setField` logs every fill (`ok/FAIL [type] label <- value (N ms)`) and delegates to the adapter. `timed()`.
- `shared/dom.js`: React event simulation (`click`, `kbd`/`key`, `typeInto`, `nativeSet`).
- `shared/matching.js`: `expandWants`, `scoreOpt`, `bestOption`, `hasPhrase`, `hasPosPhrase`, abbreviations, `matchAlts` (the ordered-fallback matcher).
- `shared/highlights.js`: blue/yellow `mark` / `unmark` / `clearMarks`.
- `shared/controls.js`: setters for native controls shared by every portal: `choiceOptions` (option text via `optionText`: the `<label for>` anywhere on the page, a wrapping label, the parent when it holds only this input, the text right after / before the input or its empty wrapper up to the next control or line break, then the value with camelCase / underscores split; iCIMS Perimeter's veteran radios were read as "NotProtectedVeteran" instead of "I AM NOT A PROTECTED VETERAN"; matching is case-insensitive), `setChecked` (click + verify, see Rules: "visually checked != registered"), `setChoice` (radio / checkbox groups), `setCheckbox`, and `dataUrlToFile` (the saved resume as a File).
- `shared/ui.js`: floating "Autofill page" button, the progress `toast` ("Filling…") and `hideToast`.
- `shared/donetoast.js`: the Done toast ("Done." / "Stopped."), and the "Autofilling… <step>" panel with its Stop button (`globalThis.AAF_PROGRESS_PANEL(data, opts)`, same spot; the toast removes it); both self-contained (`globalThis.AAF_DONE_TOAST(data, opts)`), loaded by every content-script entry (after ui.js) and by background.js (`importScripts`), which injects exactly this function into the top frame of an embedded form's tab (see Rules: "The Done toast").
- `shared/profile.js`: `profileValue` (contact fields, fixed answers via `FIX`, the `GOV_ATTEST` guard, named-employer rule, EEO, graduation), `isPreferred`.
- `shared/learnrules.js`: what may be learned, with no dependencies (`globalThis.AAF_LEARN_RULES`): `blockedCategory(q, type, a)`, `categoryOf` (Options' category tags), `SENSITIVE`, `AVAILABILITY_Q`, `NOTICE_Q`, `COMPENSATION_Q`, `FILE_Q`, `LOCATION_Q`, `TRAVEL_Q`, `RESTRICTION_Q`, `pruneDeleted` (30 days). Loaded by every content-script entry (before learning.js), by background.js (`importScripts`, the purge) and by options.html, so the three can't drift apart.
- `shared/prefmap.js`: preference mapping (`globalThis.AAF_PREFMAP`, no dependencies, also loaded by options.html; loaded after learnrules.js in every content-script entry): `ROLE_AREAS` (the Options "Role interests" checklist), `ROLE_SYNONYMS` (area -> option wordings), `mapLocal`, and the content-side `AAF.mapPreferences(f, { areas, what, synonyms }, options)`, which adds one Haiku call (background.js `MAP_PREFS` / `mapPrefs`) for options the synonym map can't place. Reusable for any "map my checked preferences onto this form's options" question: a rule returns `{ prefMap: { areas, what } }` and `AAF.setField` (core.js) reads the options, maps them, and hands the adapter `{ checkAll }` (checkbox groups) or exact steps (single choice, the first in your order).
- `shared/learning.js`: `AAF.state` (profile, settings), `findLearned`, `learn`, `learnBlock`, `SENSITIVE` / `isSensitive`, `AVAILABILITY_Q`, `onApplicationPage`.
- `shared/job.js`: `AAF.jobInfo()`: the posting's `{ location, description }`, read once per page URL and logged (`job location: "..." (from ...); job description: N chars (from ...)`). It asks the adapter's optional `jobInfo()` first, then schema.org JobPosting JSON-LD on the page (`jobFromLD`). Helpers: `htmlToText`, `fetchDoc` (same-origin page fetch), `fetchJSON`. Only called when needed: an office-attendance question is on the page, or there are drafts.
- `adapters/workday.js`: Workday field discovery (`fieldContainers`, `describe`, `getLabel`), widget setters (listbox dropdowns with scrolling and retries, multiselect search prompts, radios, checkboxes, date sections), repeatable sections (work experience, education, websites with `onlyEmpty`, languages, skills), resume upload, and the DOM wiring for learning.
- `shared/form.js`: `AAF.makeFormAdapter(cfg)`, the toolkit for single-page React application forms (Greenhouse, Ashby). It returns a complete adapter: control-first label-driven discovery (inputs, selects, textareas, comboboxes, Yes / No button toggles), react-select / combobox / native-select / toggle / date / autocomplete setters, `live` / `retryIfDetached` / `waitQuiet` for re-renders, resume upload, the education step (`fillLate`), learning wiring. - `adapters/rippling.js`: Rippling config for `makeFormAdapter`: form root by structure, custom-question labels (`fieldInfo`), the popper dropdowns (`customSelect`), the location autocomplete, resume parse wait, job info (see "Rippling quirks").
- `adapters/yc.js`: YC Work at a Startup: the apply dialog's note to the founder (see "YC Work at a Startup"). Not a `makeFormAdapter` config.
- `shared/main.js`: picks the adapter whose `detect()` matches, runs `fillPage()` (adapter sections, then the generic field pass, retry pass, and Claude), shows the button on form pages, and handles the FILL / PING messages. After the adapter sections it logs `fields found: N (text 3, radio 2, ...)`, plus the form root when the adapter has `rootInfo()`; zero fields logs `NONE: the adapter's selectors don't match this page`. A fill that silently finds nothing is otherwise invisible (the first real Ashby run logged only the resume upload).

## How we work
The working rules for every round (each report from a real page):
- Reproduce first: build a fixture with the exact wording and options reported (say which parts are reconstructed when only the start was quoted), run it on HEAD and confirm it shows the reported failure before changing code. When the fixture doesn't reproduce it, find the branch the real page must have taken (the log lines are the evidence) and change the fixture until it does.
- Fix in shared code, by meaning, for every portal: no site-specific hacks. A rule answers from the profile / Options or leaves the field yellow; eligibility, EEO, pay, start dates, attestations and relationships never go to Claude.
- Every rule that matches must answer or log why it gave up: no silent fall-through to the classifier or Claude.
- Add corpus lines for the field values and `!LOG` guards for the reported failure, plus the control cases (the variant that must stay yellow).
- Run `tests\run.ps1 -Before HEAD` (the full suite, not only the new fixture) and report before / after: what the new fixtures show, every other fixture that differs and why (log-only or a value change), the corpus and request-check results.
- Update CLAUDE.md: the incident (portal, the question, what went wrong; a fictional company name), the rule as it is now, the fixture name, and the corpus count.
- Commit and push only when asked (usually "Commit and push" at the start of the next request); no double quotes in commit messages (they break the PowerShell here-string); stage the round's files by name.
- Never: navigate or submit a page, put personal data or a real company name in any committed file, print or save an API key, delete user data.
- Report plainly: what was fixed, what is assumed (real markup not seen), and what is still open.

## Meanings, classification, regression corpus (structure)
- Rules give a MEANING, the mapper picks the option (all portals). A rule's "Yes" / "No" / "None" / "N/A" is a meaning; when a choice field has no option with that literal text, `AAF.setField` (shared/core.js) maps it: first the field's own chooser when the rule set one (`f.yesAlt` / `yesOption`: your country for work authorization, "I am a U.S. person", "None" for sponsorship), then the shared mapper `AAF.mapMeaning` (shared/prefmap.js): exact, then synonyms (yes = "I am / I can / I do / I have / I will / Correct ...", never a negated option; no = "I am not / I have never / I cannot / Never ..."; none / n/a = "None", "Not applicable", "Does not apply"; never "Other" / "Prefer not to say"), then one Haiku call (background.js `MAP_MEANING` / `mapMeaningAI`) that may only choose among the given options to express the given meaning (page text as data; null when none clearly says it). Not when an option has the literal text (the fill failed for another reason). Logged `meaning "yes": options [...] -> "I am 18 or older" (same meaning)`, not as a FAIL of the literal "Yes"; FAIL only when nothing expresses it.
  - Ranked choices for meanings that depend on the profile: relocating to where you already live ("Are you able to relocate to NYC?" with an NYC address) is "yes, local": an "I am local ..." option first, then a yes, then "open to relocating", never a negated one (`yesOption("relocation local")`), whatever the relocate setting says; logged `relocation: "nyc" is where you live (your address) ...`.
- Classification before Claude (main.js `classifyAsks`, background.js `CLASSIFY_ASK` / `classifyAsk`, Haiku): every question no rule answered is sorted into one category (work authorization, sponsorship, residence, relocation / office, education status, military / government history, EEO, compensation, start date, referral, attestation, disclosure, open-ended, other). Only "other" goes to the Claude answer call; "open-ended" (text / textarea, not a link box) is drafted; work authorization / sponsorship / relocation / military-government history use their Options settings (military: every named kind No = No), blue, through the meaning mapper; every other category stays yellow, never Claude. Logged `classified <category>: ...` and `question classifier (<model>): N work authorization, ...; N to Claude`. Classifier unavailable (no key, error, test stubs): every question goes to Claude as before.
- The classifier routes, the rules answer (Flarewave: "Which office location(s) are you interested in?" was classified relocation / office and left yellow): for a classified question main.js re-runs the rules with the category and the field's options (`profileTarget(f, { category, options })`). "relocation / office": a list of 2+ places is an office preference (your accepted locations, same-city fallback), a Yes / No question office attendance (the office it names or the job location, read for it), relocation questions the relocation rule. A value = filled and blue, logged `classified <category>: the <category> rules decide: ...`; the rules leaving it for you = yellow (`... the rules leave it for you`); no rule = the category's Options setting as before, else yellow. Also the office-preference pattern takes "(s)" / plurals ("office location(s)", norm's "location s"). `tests/fixtures/ashby-office-classified.html`.
- Tessera (the third repeat, after Flarewave and 2Password): "Location (where you will be based while working)" (an Ashby location search box) was "classified relocation / office: left for you". The dispatch was in the code but couldn't help: the location rule took only labels of 40 characters or fewer, and the dispatch's office rules decide from the field's options, which a search box doesn't have until typed. Now a label that STARTS with the question is the location question whatever follows (the parenthetical / first sentence set aside: "Location", "Current / Your location", "Where are you (currently) based / located", "Where will you be based / working from"), and a classified relocation / office question about a place to be (location / based / city / metro / home base) on a search box with no options goes to the location rule. Order of operations, unchanged: the rules first (by label), the classifier only for questions no rule matched, then each category back to its rules (`profileTarget(f, { category, options })`), the Options setting next; yellow only when none decides. `tests/fixtures/ashby-location-long.html` (three wordings, one only the classifier recognizes); the corpus's `!LOG` lines assert that no Flarewave / 2Password / Tessera question is "left for you" by the classifier.
- The 4th repeat (an embedded Greenhouse form): "Are you based out of the New York City Metro area?" was "classified residence: left for you". The residence rule took only "reside / live / based / located IN <place>", and "residence" had no dispatch at all. Now the rule also takes "based out of / located near / within / in or around", a classified residence question goes to it (the place after its last in / out of / within / near / around / local to / close to), "the tri-state area" counts for a NY / NJ / CT address, and an NYC address (a borough, or a neighborhood with an NYC zip) is New York City / NYC / "the NYC metro / Metro area". Every category's dispatch (main.js `classifyAsks`, listed in a comment above `settingFor`): work authorization / sponsorship -> their rules, then the Options answer through the meaning mapper; residence -> the residence rule; relocation / office -> the office / location / relocation rules, then the relocate setting; education status -> the studying-now / school / graduation rules; military / government history -> the Options history answers; EEO -> the EEO rule its options point to (veteran / disability / gender / race / orientation wordings; logged `classified EEO: the options are veteran status options -> the veteran status rule`); referral -> the how-did-you-hear list when the options are sources; open-ended -> drafts; other -> Claude. No rule by design (always yours, never Claude): compensation, start date, attestation, disclosure. ## How answers are chosen (order matters)
The main pass is a queue, not a one-time list (shared/main.js): answering a question can reveal a follow-up (DataPilot: "If hired, can you provide proof of eligibility?" appears only after "Are you legally permitted to work..." = Yes, and used to be missed: discovery ran once, and the retry pass only refills fields with a profile answer). A MutationObserver notes new elements; before the next field the form is re-scanned (`discoverFields`, keyed by id + label + position) and unseen fields are inserted right after the one just handled, logged `new field revealed: <label>`. When the queue runs out, up to 3 more passes look for anything still unseen. Revealed fields go through the same steps below (all portals). `tests/fixtures/workday-conditional.html` has a two-level follow-up chain.
Late reveals: an answer given by Claude, a draft, or a re-fill in the final sweep can also reveal a follow-up (Lexidos: "5a. Expected degree completion date" appears only after Q5, which Claude answered at the end, so 5a was never discovered). After the Claude / draft round and again after the final sweep, `lateReveal` re-scans (after 400 ms), runs new fields through the same queue (`runQueue`), and sends new unknown questions to Claude in one more round (`askRound`); up to 2 rounds each time, logged `late reveal after Claude: N new fields`. Unanswered questions are marked yellow once, at the end (`markLeft`). `tests/fixtures/workday-late-reveal.html`: Q6, answered only by Claude, reveals 6a, which goes to a second Claude round.

0. Sensitive fields are skipped entirely. Named-employer questions come next (`namedEmployerAnswer`, see Rules), then government / military history questions (`govHistoryAnswer`, from Options; see Rules). Then government / defense attestations (`GOV_ATTEST`) take an exact learned answer or get the yellow mark; nothing below applies to them.
1. Profile fields matched by label + `data-automation-id`. A field that already holds a value is compared first (see Rules: "Prefilled values").
2. Fixed answers (work auth, sponsorship, 18+, previously worked here, clearance, US person, willing to travel, employment restrictions). Never sent to AI.
3. Learned answers (saved when the user answers a skipped question; exact or Jaccard >= 0.85 match).
4. Claude, only above the confidence threshold. A Claude or draft answer never overwrites a field that got filled after the question was collected (a portal's resume parse); that's logged `was filled meanwhile ..., kept it`. Open-ended textareas instead get a draft (draft mode, see Rules), unless the form demands the candidate's own writing (`noAI`, left yellow). Blue outline = auto-answered, yellow = needs the user. Every Claude call logs `[autofill] Claude: ...`: the model, any error, and each answer with its confidence and why it wasn't used. A Claude error is repeated in the final "Done" toast, because the final toast replaces earlier ones.

## Workday quirks learned so far
- React app: set values via the native value setter + input/change events, and simulate pointer/mouse event sequences for clicks.
- Text inputs only commit to Workday's React state on real typing + focusout. Setting the value in one shot shows the text but validation still says "required and must have a value". `el.focus()`/`el.blur()` fire no events when the page isn't focused, so `typeInto()` dispatches focusin/focus, clears, then per character keydown/keypress/beforeinput/native set/input(insertText)/keyup, then change/blur/focusout explicitly. Use `typeInto()` for every text, textarea, date section, and multiselect search fill.
- Dependent fields re-render: setting Country replaces the State field, so containers captured at the start of `fillPage()` can be detached. The main loop re-finds a detached field by `data-automation-id` + label (+ order among duplicates), `setDropdown` waits ~400ms after a pick, and a retry pass after the main loop re-scans and refills any profile-mapped field that still isn't filled. Only fields that fail the retry get the yellow mark.
- Dropdowns are `button[aria-haspopup="listbox"]` + `[role="listbox"]` popups. Synthetic option clicks select the value but may leave the popup open, so `ensureClosed()` escalates Escape -> outside click -> toggle button. Always close stale popups before opening another (`ensureAllClosed`).
- Wrong-popup clicks (BoFL Application Questions: "Are you currently an active contractor working at Bank of Fictionland?" logged "ok <- No" but showed "Select One"; the PcC question was "filled twice"). One cause for both: `listboxFor` falls back to "the newest visible listbox" when a button's own listbox can't be told (no aria-controls), and the previous question's popup was still on screen (closing). The next dropdown took it for its own and clicked "No" in the previous question's list. `tests/fixtures/workday-questions.html` reproduces it: on the old code every answer landed in the previous question (PcC "Yes", work authorization "No", sponsorship "Yes"), all logged ok. Fixes:
  - `openDropdown` waits (up to 800 ms) for a visible popup to go away, notes which popups are already showing, and `listboxFor` never returns one of those.
  - Every dropdown pick (`setDropdown`, `chooseStep`) is confirmed: the button (re-found if re-rendered) must show the chosen option within 1 s (`confirmPick`). If not: `picked "No" but the button shows "Select One"; trying once more` with the exact option; still not: `didn't register ...; left for you`, FAIL, and the field gives up (`data-wdaf-gave-up`), so the retry pass marks it yellow.
  - `ensureClosed` toggles the button only when the button itself says it's open (a popup merely fading out made it reopen closed dropdowns), and waits up to 800 ms for a closing animation before logging "popup still open".
- Every dropdown opens through `openWithOptions`. It waits until the listbox (still connected) shows at least one real option, not just "Select One". If it doesn't, it closes all popups, waits 400ms, and reopens, up to 2 retries, logging each failed attempt with the listbox id and aria-controls. Right after a search box, the first dropdown can be read before its listbox renders, or a stale popup can still be closing: PcC's English Language dropdown read 0 options while Italian's, a moment later, worked.
- The `ok` log line shows the option or text actually selected (`<- No`, `<- Home Cellular`), not the requested fallback list or steps. Adapters record it in `f.picked`. FAIL lines still show the requested value. (This changed Workday's log lines against `workday-v2`; values and outlines are unchanged.)
- A blank profile value logs `skip ... skipped (blank in profile)`, not FAIL. Log values go through `show()`: arrays are joined and objects JSON-stringified, never the console's "Array(3)" / "Object".
- An array returned by a profile rule is an ORDERED FALLBACK list, never multiple values: `[p.source, "Social Media", "Job Board"]` (How Did You Hear) and `["United States of America (+1)", p.phoneCountry]` (Country Phone Code: Workday's own name carries the code, and the bare name returned "No Items" on BoFL). Before searching, a search field whose chips already hold any alternative is skipped (`chipMatches`: exact, ignoring a "(+N)" suffix). Workday often pre-fills the phone code from Country. For these single-value fields (not skills), "already selected?" also accepts a chip that strongly matches (score >= 85), so an earlier "LinkedIn Jobs" pick counts for "LinkedIn". In `setMulti`, a click succeeds when its checkbox is ticked, the chip count goes up, or the clicked option's text is now a chip (single-select prompts replace the chip). This judges the click, not the wanted value: on NVEXA, "LinkedIn Jobs" picked for "LinkedIn" was judged a failure, and the fallbacks were searched too. Search fields stop at the first that gets selected, dropdowns take the first alternative with a strong (then weak) match over the full option list, and radios take the first alternative that matches. Multiple chips only come from `fillSkills` (one `setMulti` per skill). BoFL once added all three "How did you hear" values.
- Skills with "+" (Fortuna): "Microsoft Visual Studio C++" and "C++ Programming Language" timed out after 12 s, with results showing only "Microsoft Visual Studio C" / "C Programming Language": Workday's search treats "+" like a space. `setMulti` first checks the search box holds exactly the typed text (else sets it with the native setter + input event, logged). When no alias of a "+" skill is found, `fillSkills` searches shorter terms: each alias without its "+" word ("Microsoft Visual Studio", "Programming Language"), then the "+" word alone ("C++"), and accepts only a strong match of one of the skill's names (`setMulti`'s `search` option: type one thing, match another). `norm()` keeps "+" and "#", so "C Programming Language" never equals "C++ Programming Language". Logged `skill "..." found by searching "..." (the search ignores "+")`.
- Skill search speed (Fortuna: 89 skills in 365 s; Example Cloud AI 79 s, Virtualization 59 s, LevelDB 35 s): a search that returned results, none an exact match, waited the full 12 s per alias; only an empty "No Items." list stopped early. Skills pass `settleMs: 2000` to `waitForResult`: once this search's own results (changed since Enter, non-empty) stay the same for 2 s without a strong match, it stops (`stopped: results without an exact match`), and 2 s of an unchanged "No Items." ## Rules
- HARD RULE: the extension must never navigate pages. Never click Save and Continue, Submit, Back, Next, or any other page-level control; the user reviews and submits. This is enforced in `click()` (shared/dom.js, `navBlockReason`). It refuses buttons/links whose text is Back, Next, Continue, Save and Continue, Submit, Apply, Cancel, Exit, Send / Send message, Close, Sign Out / Log Out, or Review; links that navigate (`a[href]` other than `#` / `javascript:`); and controls whose `data-automation-id` matches footer / navigation ids (`pageFooter*`, `bottom-navigation*`, `*BackButton`, `*NextButton`, `*SubmitButton`, ...). It logs `BLOCKED click on ...`. The only exception is controls inside an open popup / listbox. Dropdown buttons (`aria-haspopup`) are never judged by their text, since it shows their value. Never search the whole document for a control to click ("back", "close", ...); look only inside the open popup. A document-wide "back" lookup once clicked Workday's footer Back button and closed an NVEXA application.
- Visually checked != registered (all portals). A checkbox, radio or toggle can show as selected while the portal's React state never changed. Ashby (Chainmail Labs): "How did you hear about us?" showed LinkedIn ticked, the log said `ok [checkgroup] ... <- LinkedIn (10-16 ms)`, and submit failed with "Missing entry for required field". The old setter clicked the <input> first and accepted `checked` at once; the portal's handler evidently isn't on the input. Always use real click events and verify (`setChecked` in shared/controls.js, used by `setChoice` and `setCheckbox`):
  - Never set `.checked`. Click what a user clicks, with the full pointer / mouse sequence: the label (`label[for]` or the enclosing label), then a styled `role=checkbox|radio` element, then the input, then its parent.
  - After each click, verify `checked` AND `aria-checked` (input or styled element). Not in the wanted state (no effect, or toggled twice by label + input handlers): click the same target once more.
  - Wait 300 ms and verify again: a controlled React input reverts what its state didn't take. Reverted = not registered, next target (logged).
  - Then dispatch input / change and focusout / blur on the input.
  - A fill that needed a fallback target logs `registered after clicking the <target> (tried ...)`; a failure logs the state and the option's HTML.
  - Yes / No toggles (`setToggle`, shared/form.js) are verified the same way: `aria-pressed` (rendered from React state) must still hold 300 ms after the click.
  - Toggle state (Vellum, Ashby: "Are you authorized to work for any employer in the United States of America?" showed "Yes", submit said "Missing entry for required field"; sponsorship right below passed): when the group's buttons carry aria state (aria-pressed / -checked / -selected), only that counts; a class is styling (`pressed`). Before, an "active" class alone (hover / focus styling) passed for selected even with aria-pressed="false", so the prefill check logged `kept "Yes" (matches your profile)` and never clicked. Registered (`toggleRegistered`) also needs Ashby's mirror checkbox to agree (Yes = checked, No = unchecked). A toggle that looks selected but isn't registered is clicked (logged with each button's aria-pressed / class and the mirror); not registered after the click: one more click unless the button now reads pressed; still not: FAIL with the group's HTML. Not confirmed on the real page yet (no markup of that field); the fixture reproduces the stale-class case. Since Old Harbor, Ashby answers are also set through the hidden checkbox and every Yes / No is checked at the end of the fill (see Ashby quirks).
  - Every pass checks registration, not the visual: the adapter's `registered(f, picked, wanted)` (shared/form.js: toggles as above; radios = the picked option's input checked and not aria-checked="false"; checkbox groups = some option checked, none aria-checked="false"; single checkboxes = as wanted). The retry pass treats an unregistered radio / toggle / checkbox group as not done and re-clicks it; the final verification sweep re-checks every radio / toggle / checkbox filled this run (`"No" is not registered after the fill ...; clicking it again`). Both log `re-registered: <label>` when a re-click takes. `tests/fixtures/ashby-survey.html`: a stale "_active_" class on work authorization's Yes, the 18+ toggle reset when the survey is first answered (retry pass), and sponsorship reset by the retry pass's 18+ click (final sweep).

## Roadmap: multi-portal
Goal: one extension, one shared profile / learned answers / Claude setup, with a per-portal adapter.
- Refactor done: shared logic lives in `shared/`, and portal-specific discovery, widgets and quirks in `adapters/<portal>.js`. The adapter is picked by `detect()` (hostname). It was a pure refactor: on headless-Edge test pages, logs, stats, field values and outlines were identical before and after.
- Adding a portal: write `adapters/<portal>.js` implementing the adapter interface (see Files). Reuse `AAF.setField`, `typeInto`, `bestOption` / `matchAlts`, `mark`, and `profileValue` rather than copying them. Add its hosts to `host_permissions`, then either add a new `content_scripts` entry (the shared files, `shared/form.js` if it uses the toolkit, the new adapter, then `shared/main.js`) or add the adapter to the existing list and its hosts to `matches`. Keep `shared/main.js` last. The popup picks its injection fallback by matching the tab URL against each entry's `matches`, so a new entry needs no popup change. Add a `tests/fixtures/<adapter>-*.html` page and run `tests\run.ps1`; existing fixtures must stay identical.
- Workday: `adapters/workday.js` (myworkdayjobs.com, myworkday.com, myworkdaysite.com).
- Greenhouse: `adapters/greenhouse.js` (boards / job-boards, plus the embedded iframe via `all_frames`). Tested on real postings (tagged greenhouse-v2).
- Lever: `adapters/lever.js` (jobs.lever.co, jobs.eu.lever.co, plus the embedded iframe via `all_frames`), a config for `shared/form.js`. First real posting (ShopForward) fixed the location label, upload check and confirmation card.
- iCIMS: `adapters/icims.js` (`*.icims.com`, the form inside `icims_content_iframe` via `all_frames`), a config for `shared/form.js` plus `delegateFill` / `passiveFrame` / `restrictTo` / `customSelect`. Fixed from the first real posting (HMSY); awaiting a retest.
- Rippling: `adapters/rippling.js` (ats.rippling.com, plus embedded iframes via `all_frames`), a config for `shared/form.js` plus `customSelect` (the popper dropdowns), built from a real form; awaiting a first real run.
- Gem: `adapters/gem.js` (jobs.gem.com, plus embedded iframes via `all_frames`), a config for `shared/form.js`. First real posting (Nuvix) fixed the form root, labels, radio grouping and upload check; the posting header is still unseen.
- Ashby: `adapters/ashby.js` (jobs.ashbyhq.com, plus the embedded iframe via `all_frames`), a config for `shared/form.js`. First real posting (Parallax) fixed discovery; awaiting a retest.
- A new single-page React portal (Lever, ...) should start as a `makeFormAdapter` config, adding options to `shared/form.js` only for quirks it really needs.
- YC Work at a Startup: `adapters/yc.js` (workatastartup.com, ycombinator.com/companies/*): drafts the apply dialog's note to the founder for the user to rewrite and send. Never sends. Unverified until tested on a real page.
- Add each new host to `host_permissions` and `content_scripts.matches` in manifest.json.

## Workflow notes
- Storage is tied to the extension ID, and an unpacked extension's ID depends on its folder path. Moving or renaming the folder resets saved data: export a backup from Options first, then import.
- Keep the project in git so every change can be reviewed and reverted.
